# Design: Language Infrastructure (Phase 5)

**Date:** 2026-10-10
**Status:** Draft — awaiting owner review
**Parent spec:** `2026-09-19-nextjs-portfolio-design.md` (§4 localized variants, §9 internationalization)
**Branch:** `feat/i18n`

---

## 1. Purpose and scope

Build the language system so Hindi and Telugu can be added later by translating
content and flipping one switch. **No translations ship in this phase** (owner
decision). English stays the only published language, and every current URL is
unchanged.

### Success criteria

1. **Locale list:** `src/content/locales.ts` lists `en` (published), `hi` and `te` (both
   unpublished), each with its native name and `lang` attribute.
2. **Placeholder content:** `content/hi/` and `content/te/` exist and, for now, re-export
   the English content. Replacing them with real files is type-checked against the
   same `HomeContent` / `CaseStudy` types.
3. **English URLs unchanged:** `/` and `/work/<slug>`. `/en` and `/en/...` redirect
   (308) to the unprefixed URL.
4. **Unpublished locales:** `/hi`, `/te` and anything under them return a real 404.
5. **Language switcher in the header:** English is marked as current; हिन्दी and తెలుగు
   are disabled and labelled "Coming soon". It uses a native `<details>` element with
   zero JS. A published locale's entry becomes a link to the same page in that
   language.
6. **`<html lang>`** comes from the route's locale.
7. **No regressions:** every existing test, the confidentiality guard and the LHCI
   budgets pass unchanged.

### Out of scope (documented for later, §6)

- Hindi and Telugu translations.
- Noto Sans Telugu and Devanagari fonts.
- `hreflang` alternates.
- Any `Accept-Language` redirect.

### Deviation from the parent spec

Parent §3 and §9 named **next-intl** with JSON catalogs. This phase follows the
approach in **Next 16's own internationalization guide**
(`node_modules/next/dist/docs/01-app/02-guides/internationalization.md`): a `[lang]`
segment, per-locale dictionaries and Proxy, with no library.

- **Why:** our typed TS content modules already are dictionaries, with stronger
  checks than JSON (`tsc` fails on a missing field), and no library keeps the client
  JS budget intact.
- **Effect:** CLAUDE.md's "Planned stack" and "Content is typed TypeScript modules" lines
  are updated to match.

## 2. Routing

| Request | Result |
|---|---|
| `/`, `/work/<slug>` | Proxy **rewrites** to `/en/...`. The URL in the browser is unchanged. |
| `/en`, `/en/...` | **308 redirect** to the unprefixed path (one canonical URL per page). |
| `/<unpublished>/...` (`/hi`, `/te/work/x`) | Rewrite to a non-route, which gives a **404** with `noindex`. |
| `/<published non-default>/...` (future) | Served as is. |
| `/work/<unknown>` under any locale | **404** (the 4a behaviour, kept). |
| Static files, `/_next`, `icon.svg`, the resume PDF | Untouched (excluded by the Proxy matcher). |

- **App structure:** pages move under `src/app/[lang]/`, i.e. `[lang]/layout.tsx` (the
  root layout, which sets `<html lang>`), `[lang]/page.tsx` and
  `[lang]/work/[slug]/page.tsx`.
- **Static params:** `generateStaticParams` returns **published** locales only (today
  `en`).
- **Default for unknown `lang`:** pages call `notFound()`.
- **The global 404 page** must still render with the site chrome. The exact mechanism
  (`not-found.tsx` under `[lang]` or `global-not-found`) is confirmed in the prototype
  and recorded in the plan.

### Helpers (`src/lib/i18n.ts`, pure and unit-tested)

- `isLocale(x)`
- `publishedLocales()`
- `localizedPath(locale, path)`: `"en"` gives an unprefixed path; others get a `/hi`
  prefix.
- `splitLocale(pathname)`: returns `{ locale, rest }`.

Proxy, the switcher and the pages all use these, never string concatenation.

## 3. Content

```
src/content/
  locales.ts        # Locale list + publish switches
  en/               # real copy (unchanged)
  hi/index.ts       # export * from "../en"  (placeholder until translated)
  te/index.ts       # export * from "../en"
  index.ts          # getContent(locale): { homeContent, caseStudies, caseStudyUi }
```

- Components receive content for the current locale. `@/content/en` imports in pages
  become `getContent(lang)`.
- **Switcher labels:** the `LocaleSwitcher` label text ("Language", "Coming soon") lives
  in each locale's `homeContent.site`, so it's translatable too.

---

## 4. Language switcher

- **Markup:** `<details>` + `<summary>` (zero JS; keyboard and screen-reader friendly by
  default). The summary shows a globe icon and the current language's native name.
- **List entries:**
  - **Current language:** text with `aria-current="true"`.
  - **Published other language:** an `<a href={localizedPath(other, samePath)}>` with
    `lang` and `hrefLang` set.
  - **Unpublished language:** a non-interactive `<span aria-disabled="true">` showing
    the native name plus a "Coming soon" note. Its `lang` attribute lets screen readers
    pronounce it.
- **Placement:** the header, between the section nav and the theme toggle. It is visible
  at every width; below `md` the nav is hidden, but the switcher still shows.
- **Styling:** tokens only; the menu is a surface card with a hairline border.

## 5. Testing

- **Unit:**
  - `i18n` helpers: round-trips, `en` unprefixed, unknown locales;
  - `locales` invariants: exactly one default, `en` published;
  - `getContent` returns English for `hi`/`te` today;
  - switcher states: current, disabled "Coming soon", and the published-link branch via
    a test locale list.
- **E2E:**
  - all existing specs pass unchanged;
  - `/en` → 308 → `/`, and `/en/work/x` → `/work/x`;
  - `/hi`, `/te`, `/hi/work/pharma-enterprise-portals` → 404;
  - `<html lang="en">`;
  - the switcher opens with the keyboard and shows "Coming soon" entries;
  - axe on the home page with the switcher open, in both themes.
- **LHCI:** budgets unchanged.

## 6. Publishing a language later (runbook)

1. Translate: replace `content/<lang>/index.ts` with real `home.ts` and
   `case-studies.ts` files (`tsc` flags anything missing). The owner reviews every line.
2. Add the native-script font (Noto Sans Telugu or Devanagari) as a local subset per
   `src/fonts/README.md`, loaded only for that locale's layout.
3. Add `hreflang` alternates for published locales in the metadata.
4. Flip `published: true` in `locales.ts`. Proxy, static params and the switcher follow
   automatically.

## 7. Decisions log

| Decision | Choice | Why |
|---|---|---|
| Translations | none in this phase; `hi`/`te` re-export English | owner decision |
| Library | none (Next's documented approach) | zero client JS; typed TS dictionaries are stricter than JSON |
| English URLs | unprefixed, via Proxy rewrite | nothing already shared breaks |
| `/en/...` | 308 to unprefixed | one canonical URL per page |
| Unpublished locales | 404 | no English pages masquerading as Hindi/Telugu |
| Switcher | visible, with disabled "Coming soon" entries | owner: "under development" |
| Switcher tech | native `<details>` | zero JS, accessible by default |
| Fonts and hreflang | deferred to publish time (§6 runbook) | untestable without content |
